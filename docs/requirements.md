# TEA-V1 要件と受入条件

PLAN_VERSION: `TEA-V1.0`

## 状態の定義

- 計画済み: 要件IDと受入条件が本書に記載されている。
- 実装済み: 対応コードと必要なテストが存在する。
- 検証済み: 受入条件に対応する検証が実行され、成功している。

本書の全要件は計画済みである。実装済み・検証済みの現在状態は`docs/status.md`を正とする。

## 機能要件

### TEA-FR-001 ダッシュボード

単一事業所の製造、在庫、出荷の概況を一画面で確認できること。

受入条件:

1. 製造状態ごとの製造指示件数を表示できる。
2. 原料在庫と製品在庫の概況を表示できる。
3. 指定した集計期間に対応する入荷、製造完了、出荷の数量を表示できる。
4. 取得中、データなし、APIエラーを文字情報でも判別できる。
5. 表示値が集計APIの応答と一致する。

### TEA-FR-002 原料入荷

仕入先から入荷した原料を登録・参照し、原料在庫へ反映できること。

受入条件:

1. 入荷日、仕入先、茶葉、品種、数量を登録できる。
2. 必須項目、日付、正の数量、参照マスタの有効性をfrontendとbackendで検証する。
3. 登録成功時に入荷記録、原料在庫残高の加算、入荷種別の増減履歴が同一transactionで保存される。
4. いずれかの保存に失敗した場合は全更新がロールバックされる。
5. 一覧を`page`、`page_size`で取得し、詳細を参照できる。

### TEA-FR-003 製造指示

製造対象、予定数量、使用原料、使用設備を含む製造指示を登録・参照できること。

受入条件:

1. 製品、予定数量、予定日、使用原料と予定使用量、設備を指定して下書きを登録できる。
2. 必須項目、日付、正の数量、マスタの存在と有効性をfrontendとbackendで検証する。
3. 一覧を状態その他の定義済み条件で絞り込み、`page`、`page_size`で取得できる。
4. 下書きの内容を編集できる。
5. 下書き以外では`TEA-FR-010`の制御に従い、禁止項目を変更できない。
6. 詳細で状態、原料、設備、工程実績、関連在庫履歴を確認できる。

### TEA-FR-004 工程管理

製造指示に対する工程の進捗と実績を登録・参照できること。

受入条件:

1. 製造指示に紐づく工程を定義順に表示できる。
2. 製造中の指示に対して工程の開始・完了日時と実績情報を登録できる。
3. 下書き、指示済み、完了、取消の指示には工程実績を登録できない。
4. 工程順序に反する完了操作をbackendが拒否する。
5. 工程情報の具体項目は詳細設計で確定し、本要件の範囲を変更しない。

### TEA-FR-005 設備管理

設備マスタと、製造指示・工程で使用する設備情報を管理できること。

受入条件:

1. 設備コード、設備名、有効・無効を登録・編集・参照できる。
2. 設備コードの重複をbackendとDB制約で拒否する。
3. 設備は物理削除せず有効・無効で管理する。
4. 無効な設備を新しい製造指示に指定できない。
5. 過去の製造指示から無効化済み設備の参照は保持される。
6. 高度な設備予約競合管理は行わない。

### TEA-FR-006 在庫管理

原料在庫、製品在庫と、それぞれの増減根拠を参照できること。

受入条件:

1. 原料と製品を区別して現在庫を表示できる。
2. 対象、取引種別、期間によって増減履歴を検索できる。
3. 一覧を`page`、`page_size`で取得できる。
4. 在庫残高は負数にならない。
5. 残高の変更には対応する増減履歴が存在する。
6. 在庫残高を通常の画面や汎用更新APIから直接書き換えられない。

### TEA-FR-007 出荷

製品の出荷を登録・確定し、製品在庫へ反映できること。

受入条件:

1. 出荷日、製品、数量を登録し、確定できる。
2. 必須項目、日付、正の数量、有効な製品をfrontendとbackendで検証する。
3. 出荷確定時に製品在庫が不足していれば確定を拒否する。
4. 出荷確定、製品在庫残高の減算、出荷種別の増減履歴を同一transactionで保存する。
5. 保存途中の失敗時は全更新をロールバックする。
6. 確定済み出荷の再確定をbackendが拒否し、在庫を再減算しない。

### TEA-FR-008 集計

期間を指定し、原料入荷、製造完了、出荷、在庫の集計情報を確認できること。

受入条件:

1. 開始日と終了日を指定できる。
2. 指定期間の原料入荷数量、製品製造完了数量、製品出荷数量を集計できる。
3. マスタ別の内訳を確認できる。
4. 不正な期間をfrontendとbackendで拒否する。
5. 集計結果が元の業務データと一致することをDB結合テストで確認する。

### TEA-FR-009 マスタ管理

茶葉、品種、仕入先、設備、製品のマスタを管理できること。

受入条件:

1. 各マスタの一覧、登録、編集、詳細参照ができる。
2. 各マスタは一意なコード、名称、有効・無効を持つ。
3. コード重複をbackendとDB制約で拒否する。
4. マスタを物理削除せず、有効・無効で管理する。
5. 無効なマスタを新規業務データで選択できない。
6. 過去の業務データから無効化済みマスタの参照を保持する。
7. 一覧を`page`、`page_size`で取得できる。

### TEA-FR-010 製造状態と操作制御

製造状態を、下書き、指示済み、製造中、完了、取消として管理し、状態に応じた操作だけを許可すること。

受入条件:

1. 許可遷移は、下書き→指示済み、下書き→取消、指示済み→製造中、指示済み→取消、製造中→完了とする。
2. 上記以外の遷移をbackendが`409 Conflict`で拒否する。
3. frontendは状態に応じて操作を非表示またはdisabledにし、理由を利用者に示す。
4. backendはfrontendの表示状態に依存せず、現在状態をtransaction内で再検証する。
5. 完了および取消は読み取り専用とし、通常操作で再開・編集・削除できない。
6. 状態別の編集可能項目と禁止操作が`docs/manufacturing-status.md`と一致する。

### TEA-FR-011 製品マスタCSV取込

製品マスタCSVを検証し、全行が正常な場合だけ一括登録できること。

受入条件:

1. 初期対象は製品マスタだけとする。
2. ヘッダー、必須値、型、文字長、真偽値、製品コード重複、品種コードの存在と有効性を検証する。
3. CSV内重複とDB既存データとの重複を検出する。
4. 1件でもエラーがあれば製品を1件も登録しない。
5. エラーCSVに行番号、項目、コード、メッセージ、入力値を含める。
6. 全行正常なら1つのtransactionで全件を登録する。
7. 取込結果として処理状態、総行数、成功件数、エラー件数を確認できる。

### TEA-FR-012 製造指示から在庫更新までの結合処理

製造指示の状態変更と原料・製品在庫更新が一貫した導線として動作すること。

受入条件:

1. 下書きから指示済みへの変更では在庫を更新しない。
2. 指示済みから製造中への変更時に、必要原料を検証して減算する。
3. 原料不足時は状態変更、残高、履歴のすべてを更新しない。
4. 製造中から完了への変更時に、製品在庫を加算する。
5. 各状態変更、残高更新、増減履歴作成は業務イベントごとの同一transactionで行う。
6. 途中例外時はその業務イベントの全更新をロールバックする。
7. 二重開始と二重完了をbackendが拒否し、在庫を再更新しない。
8. frontend、API、service、SQLAlchemy、PostgreSQLを通す結合テストで確認する。

## 非機能・横断要件

### TEA-NFR-001 API契約と統一エラー

受入条件:

1. API pathを`/api/v1`配下に置く。
2. APIエラーJSONはトップレベルに`code`、`message`、`field_errors`を持つ。
3. `field_errors`は配列とし、項目に紐づかないエラーでは空配列を返す。
4. validation、not found、conflict、unexpected errorでHTTP statusとcodeを一貫させる。
5. 共通fetch clientが統一エラーをfrontend共通型へ変換する。

### TEA-NFR-002 ページング

受入条件:

1. ページング対象APIは正の整数`page`、`page_size`を受け取る。
2. 応答は`items`、`page`、`page_size`、`total`、`total_pages`を持つ。
3. 不正値を`400 Bad Request`またはFastAPIの統一validation errorとして拒否する。
4. `page_size`の上限は詳細設計で固定し、全対象APIで共通化する。

### TEA-NFR-003 在庫取引の整合性と重複拒否

受入条件:

1. 在庫残高と増減履歴を常に同一transactionで更新する。
2. 製造開始、製造完了、出荷確定では対象業務行と在庫残高行をロックする。
3. 状態と在庫をlock取得後に再検証する。
4. 二重開始、二重完了、二重出荷を`409 Conflict`で拒否する。
5. 競合要求または途中例外でも残高と履歴に部分更新が残らない。

### TEA-NFR-004 再現可能な開発環境

受入条件:

1. Node.js 22系、Python 3.12系、PostgreSQL 16系を固定する。
2. npm lockfileとPython runtime/development-test依存定義を管理する。
3. Docker Composeでfrontend、backend、dbを起動できる。
4. backendがCompose network内の`db:5432`へ接続する。
5. 実`.env`をGit管理せず、`.env.example`に開発用項目を記載する。
6. formatter、lint、test、build、migration checkの実在コマンドをREADMEに記載する。

### TEA-NFR-005 自動テスト

受入条件:

1. JestとReact Testing Libraryでfrontendの表示、入力、状態制御、API成功・失敗を検証する。
2. pytestでschema、API、service、DB transaction、CSV取込を検証する。
3. 在庫と集計の重要テストはPostgreSQLを使用する。
4. テストは独立して実行でき、実行順に依存しない。
5. 必須テストが失敗または未実行の状態を検証済みと記録しない。

### TEA-NFR-006 手動起動限定CI

受入条件:

1. GitHub Actionsの初期workflowは`workflow_dispatch`だけをtriggerに持つ。
2. push、pull_request、scheduleその他の自動triggerを持たない。
3. frontend test、frontend build、backend test、migration checkを再現可能なjobとして実行する。
4. 自動trigger追加は計画変更として明示承認を必要とする。

### TEA-NFR-007 要件・実装・検証の追跡

受入条件:

1. 実装とテストが対応する要件IDを追跡できる。
2. `docs/status.md`で計画済み、実装済み、検証済みを個別に管理する。
3. 承認済み計画変更だけを`docs/decision-log.md`へ記録する。
4. 計画と実装の差異を検出した場合は、実装を進める前に報告する。

## 対象外

- ロット追跡
- 賞味期限
- 複数倉庫・保管場所
- 単位換算
- 歩留まり計算
- 設備予約の高度な競合管理
- 認証、ログイン、ユーザー権限
- Playwright
- 外部サービス
- 本番デプロイ
