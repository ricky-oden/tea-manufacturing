# TEA-V1 在庫transaction設計

PLAN_VERSION: `TEA-V1.0`

対応要件: `TEA-FR-002`、`TEA-FR-006`、`TEA-FR-007`、`TEA-FR-012`、`TEA-NFR-003`

## 原則

- 原料在庫と製品在庫を分ける。
- 現在庫は残高table、変更根拠は増減履歴tableで保持する。
- 残高と増減履歴を必ず同一DB transactionで更新する。
- 残高を通常のCRUD APIから直接変更しない。
- 在庫を変更するserviceは対象業務行と在庫残高行をlockし、lock後に状態と残高を再検証する。
- quantityは正数、残高は0以上とする。

## 業務イベント別の境界

### 原料入荷登録

1. requestと参照マスタを検証する。
2. DB transactionを開始する。
3. `(tea_leaf_id, variety_id)`順に残高行を確保し、決定順でlockする。未作成時はunique制約と競合を許容するinsertで1行だけ確保する。
4. 入荷ヘッダー・明細を作成する。
5. 原料残高へ数量を加算する。
6. `RECEIPT`履歴を作成し、更新後残高を記録する。
7. commitする。

途中で失敗した場合は、入荷、残高、履歴をすべてrollbackする。

入荷は登録時に即時確定する。入荷番号再登録は`409`で拒否し、複数同時入荷は残高行lock後に加算する。

### 製造開始

1. DB transactionを開始する。
2. 製造指示行をlockする。
3. 現在状態が`ISSUED`であることを再検証する。
4. 必要な原料在庫残高行を決定した順序でlockする。
5. 全原料の残高が必要量以上であることを検証する。
6. 各原料残高を減算する。
7. 原料ごとに`MANUFACTURING_CONSUMPTION`履歴を作成する。
8. 製造指示を`IN_PROGRESS`へ変更し、開始日時を保存する。
9. commitする。

原料が1件でも不足する場合は、状態、全原料残高、全履歴を更新しない。

### 製造完了

1. DB transactionを開始する。
2. 製造指示行をlockする。
3. 現在状態が`IN_PROGRESS`で、完了条件を満たすことを再検証する。
4. 対象製品の在庫残高行をlockする。
5. 製造指示の数量を製品残高へ加算する。
6. `MANUFACTURING_OUTPUT`履歴を作成する。
7. 製造指示を`COMPLETED`へ変更し、完了日時を保存する。
8. commitする。

### 出荷確定

1. DB transactionを開始する。
2. 出荷行をlockし、未確定であることを再検証する。
3. 対象製品の在庫残高行を決定した順序でlockする。
4. 全製品の残高が出荷数量以上であることを検証する。
5. 製品残高を減算する。
6. 製品ごとに`SHIPMENT`履歴を作成する。
7. 出荷を確定済みに変更し、確定日時を保存する。
8. commitする。

製品が1件でも不足する場合は、出荷状態、全製品残高、全履歴を更新しない。

## transactionをまたぐ範囲

原料入荷、製造開始、製造完了、出荷確定はそれぞれ独立したtransactionとする。実際の製造時間をまたいでtransactionを保持しない。

```text
[入荷 transaction]   commit
[製造開始 transaction] commit
    実際の製造・工程作業
[製造完了 transaction] commit
[出荷確定 transaction] commit
```

## 重複操作と競合

- 同じ製造指示への二重開始は、最初の処理後の状態が`ISSUED`ではないため拒否する。
- 同じ製造指示への二重完了は、最初の処理後の状態が`IN_PROGRESS`ではないため拒否する。
- 同じ出荷への二重確定は、最初の処理後に確定済みであるため拒否する。
- 同時要求では行lock取得後の状態を正とする。
- 拒否時は`409 Conflict`を返し、残高と履歴を再更新しない。

## 増減履歴

| transaction type | 在庫種別 | delta | reference |
|---|---|---:|---|
| `RECEIPT` | 原料 | 正 | 入荷明細 |
| `MANUFACTURING_CONSUMPTION` | 原料 | 負 | 製造指示・使用原料 |
| `MANUFACTURING_OUTPUT` | 製品 | 正 | 製造指示 |
| `SHIPMENT` | 製品 | 負 | 出荷明細 |

履歴には変動量、更新後残高、発生日時、業務参照を保存し、残高との照合を可能にする。

## 異常系

- 原料不足: 製造開始を拒否し、`409`。
- 製品不足: 出荷確定を拒否し、`409`。
- 不正状態: 操作を拒否し、`409`。
- 参照なし: `404`。
- DB例外: rollbackし、内部情報を含めない統一`500`エラー。
- deadlock等のDB競合へのretry方針は実装前の詳細設計で決定する。

## Phase 2検証根拠

- 製造開始transactionで更新をflushした直後に強制例外を発生させ、製造状態、原料残高、製品残高、在庫履歴がすべて元のままであることをPostgreSQLで確認する。
- 強制例外は統一500形式で返し、内部例外文字列をresponseへ含めないことを確認する。
- 独立したsession／connectionから同じ製造指示へ開始を同時要求し、1件だけ成功、1件はlock待機後の状態再検証で拒否され、原料減算と消費履歴が1回だけであることを確認する。
